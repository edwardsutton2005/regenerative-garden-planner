# Architecture

## Purpose

The Regenerative Garden Planner is a client-side React application for experimenting with spatial garden layouts. Its architecture is intentionally small: explicit state, curated data, pure TypeScript domain functions, and React presentation components.

The main constraint is explainability. A conclusion shown to a user should be traceable to current garden state, structured plant knowledge, and a deterministic rule.

## Technology

- React and TypeScript
- Vite for development and production builds
- CSS for layout and presentation; shared design tokens (color, type, radius, shadow) are custom properties in `src/index.css`, and UI icons are inline SVG in `components/Icon.tsx`
- Nunito (Google Fonts) as the interface typeface
- Vitest for domain and data tests
- Oxlint for static analysis
- Client-side state only
- Development-time art tooling only (not shipped): `@google/genai` for image generation and `sharp` for image processing, run by Node scripts in `scripts/`

There is currently no backend, database, authentication system, global state library, persistence layer, or AI API. See [Planned Persistence Direction](#planned-persistence-direction) for the planned local save and Supabase accounts.

## Repository Structure

```text
src/
├── components/   React interaction and presentation
├── data/         Curated plants, relationship rules, and source registry
├── domain/       Framework-independent state operations and evaluation rules
├── App.tsx       Application orchestration and interaction state
└── main.tsx      Browser entry point
scripts/          Development-time art pipeline (generation, background removal, textures, build)
art/              Style guide, references, and approved art masters (candidates are git-ignored)
public/art/       Built app art: sprites, icons, textures, bed frame
```

The repository keeps gardening knowledge out of React components. Components may choose wording and visual treatment, but they do not define which plants are companions, what spacing rule applies, or which ecological role a plant has.

## State Model

`GardenState` represents facts about one physical garden. All lengths are inches.

```ts
type Position = { x: number; y: number }

type PlacedPlant = {
  id: string
  plantId: string
  position: Position
}

type GardenState = {
  width: number
  height: number
  placements: Record<string, PlacedPlant> // keyed by placement id
  beds: Record<string, GardenBed>         // keyed by bed id
  environment: GardenEnvironment
}

type GardenBed = {
  id: string
  name: string
  position: Position // top-left corner
  width: number
  height: number
}

type GardenEnvironment = {
  cellSize: number                                  // environmental-cell resolution
  sunlightByCell: Record<CellKey, SunlightLevel>
}
```

The garden is a rectangle with its origin at the top-left corner, `x` increasing to the right and `y` increasing downward. A position is valid when both values are finite and `0 ≤ x < width`, `0 ≤ y < height`. Positions are continuous: a non-grid position such as `(31.4, 67.8)` is valid domain state. Mutation functions validate their inputs, return new state, and treat invalid operations on an existing garden as no-ops.

Garden dimensions are currently whole multiples of `environment.cellSize` from 48 through 360 inches (4–30 feet), so the environmental cells tile the garden exactly. The setup screen asks for feet.

### Placements

A placement has its own identity, independent of position. Ids are generated by the caller (the UI) and passed into domain functions, which keeps the domain deterministic and tests able to use fixed ids. Moving a placement changes its position, not its id.

The domain does not enforce exclusive occupancy: two placements may share a position. Spatial meaning is left to the evaluators. Distance 0 is still a valid distance for spacing and interaction. The UI does not add an occupancy rule either: plants can be placed close together or overlapping.

Placements store only identity, plant, and position. Neighbor lists, cell membership, and spacing status are derived, never stored.

### Beds

A bed is a rectangle in physical coordinates. It must have a finite, positive size, lie entirely inside the garden, and not overlap another bed. Touching edges is allowed, and overlap is checked with strict inequalities. Operations that would break these rules are no-ops. Beds are independent of `environment.cellSize`, so any position and size is valid.

Plants do not reference beds. Bed membership is derived: a position is in a bed when `x ≤ px < x + width` and `y ≤ py < y + height`, the same half-open rule as environmental cells. Because beds cannot overlap, a position is in at most one bed.

`moveBed` moves a bed and every placement inside it by the same distance, as a deterministic state transition. `resizeBed` changes only the rectangle. `removeBed` leaves placements where they are. `clearGarden` keeps beds, like environment, because beds are site layout rather than planting design.

New bed names come from `nextBedName` ("Bed N", the lowest unused N). Renaming trims whitespace and ignores an empty name.

### Environment

Environmental state is separate from plant placement state. `environment.cellSize` is the resolution of cell-level environmental data (12 inches today). It is not a plant-placement resolution and does not constrain where plants can be.

Sunlight is a user-declared category per environmental cell. A missing key means sunlight has not been modeled for that cell. A position maps to the cell containing it:

```text
row = floor(y / cellSize)
col = floor(x / cellSize)
```

Cells are half-open, so a position exactly on a shared cell boundary belongs to the cell below or to the right, and every valid position maps to exactly one cell.

Clearing plants preserves environmental state; starting a new garden discards both.

## Interaction State

UI concerns are not stored in `GardenState`. `App.tsx` separately tracks:

- **the active tool**, one tagged value: `select`, `plant` (with its plant id), `beds`, `sunlight` (with its Full / Partial / Shade / Clear brush), or `eraser`. Tools are persistent brushes. The toolbar highlight, active inventory slot, cursor, and status line are all derived from this one value, so they can't disagree. The last sunlight brush is remembered separately.
- **the selection**, one tagged value: a plant, a bed, or nothing. Never both. Bed selection is shown and editable only in Select and Beds.
- **the inventory**: an ordered list of plant ids in use in this garden. A palette, never an input to reasoning, and not part of undo history. It belongs with the garden plan once persistence exists.
- **the history** (`src/gardenHistory.ts`): the garden plus `past` and `future` stacks, as pure transitions (`applyChange`, `undo`, `redo`, and a checkpoint so a sunlight stroke is one step). Up to 100 steps. No-op domain operations return the same object and record nothing. A new change clears redo. New Garden starts fresh.
- whether the catalog popup and the inspector are open
- transient feedback focus placement ids
- the plant type being dragged from the inventory, and any in-progress canvas drag (preview positions only, committed on release)
- setup-screen dimensions

The view (zoom level, scroll position, and any in-progress pan) lives in `components/CanvasViewport.tsx`, not in `App.tsx`. It is view-only and resets with each new garden.

Global keyboard shortcuts live in one hook (`components/useWorkspaceShortcuts.ts`): undo, redo, Escape (leave the tool, then clear the selection), and Delete/Backspace (remove the selection). They're ignored while typing in a field. Elements that handle a key themselves, such as a focused plant marker or bed tab, stop it from reaching the hook. View shortcuts (Cmd/Ctrl + = / − / 0 for zoom, Space held for panning) live in `CanvasViewport` with the view state they change.

Tracking ids rather than positions means inspection follows a plant when it moves.

### Coordinate Spaces and the Canvas

There are three spaces, kept separate:

1. **Physical garden space** — continuous inches; the source of truth for plant and bed positions (`GardenState`).
2. **Environmental grid** — `environment.cellSize` cells (12 inches) holding sunlight. Positions map to cells through `cellAt`.
3. **Rendering and input** — responsive pixels and pointer events, handled only in `components/`.

`GardenCanvas` is one positioned surface whose aspect ratio matches the garden, sized to fit its viewport in both directions (the viewport is a CSS size container). Everything is drawn in percentages of the garden's physical size (`left = x / width`), so the canvas can resize, zoom, and pan without recalculating anything. `CanvasViewport` owns the view: it multiplies the fit-to-screen width by a `--zoom` CSS variable, keeps the zoom anchor in place by adjusting scroll after render, and draws the scale bar from the canvas's measured size. Panning is native scrolling; drag-to-pan just sets the viewport's scroll position (in the capture phase for Space and middle-button drags, so the canvas's own tools never see them). Pointer input converts to inches through `components/canvasGeometry.ts`, which reads the canvas's on-screen rectangle at event time. No pixel value or scale factor is stored.

**Input precision and the boundary.** Plant positions entered through the UI are rounded to the nearest whole inch that is a valid position. The domain range is half-open (`0 ≤ x < width`), so the largest valid whole inch is the largest whole number strictly less than the width (computed, not hard-coded). Input from the last half inch, which would round onto the excluded far edge, lands on that value. The garden itself is unchanged: it still spans exactly `[0, width)`, domain validation is unchanged, and non-integer positions remain valid domain state. Bed rectangles are closed shapes, so bed edges may sit exactly on the garden's far edge. They snap to 6 inches, which is also only a UI choice.

**Layers**, bottom to top: grass around the garden (the viewport background); soil tiles and faint grid lines (CSS backgrounds on the canvas, no DOM cells); beds (wooden frame via CSS `border-image`, bed-soil tiles); sunlight (one element per modeled cell, blended as warm light or cool shade); spacing envelopes; plant sprites; the selected bed's name tab and handles. The Beds tool raises the bed layer to the top. Plant sprites are a fixed pixel size (44 px) and never scale with inches, so they never suggest a footprint.

**Physical units in CSS.** The canvas sets `--in`, one inch on screen, computed from the same expression as its width. Real-size styling uses it: soil and bed-soil tiles repeat every 12 inches, and bed boards are 2 inches wide, with a minimum on-screen width.

**Art assets.** `npm run art:build` (`scripts/build-art.ts`) turns the approved masters in `art/approved/` into small app files in `public/art/`. Plant sprites and icons are trimmed and resized to 128 px. Soil, bed-soil, and grass tiles are generated in code by `scripts/textures.ts`, deterministic and seamless by construction. The bed frame is composed from approved plank and corner-post art: the plank's repeat joint is cross-faded away, and the pieces are assembled into a 9-slice image for CSS `border-image`. The build also writes `src/components/artAssets.ts`, the generated list of plants with art. `components/plantArt.ts` maps a plant id to its URL, or nothing, in which case components fall back to the placeholder disc. The domain never references art.

**Pointer ownership by tool:** plant markers take input in Select, Plant, and Eraser. Only Select moves existing plants, so with a plant brush armed a click on a plant inspects it and a press that starts on a plant never places one. Sunlight painting maps the pointer to an environmental cell and paints it, with plants and beds inert. Clicks on empty canvas place a plant (Plant) or select the bed at the exact point (Select). Existing plants move by pointer drag with a grab offset. Inventory plants use the browser's drag and drop, and the canvas reads the drop point.

**Placement preview** is one `candidate` (a plant and a position) derived from whichever source is active: an existing plant being dragged, or an inventory plant dragged over the canvas. A future hover preview for an armed plant brush is another source of the same value, and reuses the same feedback path.

**Spacing envelopes** are a visualization chosen by the UI (`components/spacingPreview.ts`), not a domain concept. The domain supplies the sourced minimum and violations (`evaluateSpacing`). The UI draws the rule as a dashed circle of radius `spacingInches.min`. During a drag, feedback is computed by applying the candidate position to a copy of the garden with the existing pure operations (`movePlant`/`placePlant`) and running the existing evaluators. React never re-implements a rule.

Inspection is resolved against live garden state. Cached relationship, spacing, composition, or opportunity results are not stored in placements.

## Structured Knowledge

`src/data/` contains the normalized knowledge consumed by the application:

- plant identity, lifecycle, same-species spacing in inches, and ecological roles
- symmetric companion/incompatible relationship pairs
- a registry of attributable sources
- optional claim-level evidence references

Visual details such as colors, icons, or component names are not stored as domain facts. Evidence metadata is also kept separate from reasoning: it records provenance but does not alter a rule result.

See [docs/data-sources.md](./docs/data-sources.md) for the current sourcing policy and known provenance gaps.

## Deterministic Domain Logic

Each concern has a focused module instead of a generalized rule-engine abstraction:

- `garden.ts` — state construction, validation, placement operations, environment operations, Euclidean distance, and position-to-cell mapping
- `relationships.ts` — symmetric companion/incompatible lookup and evaluation within the interaction distance
- `spacing.ts` — same-species spacing evaluation
- `composition.ts` — garden-wide aggregation of represented ecological roles
- `opportunities.ts` — explicitly scoped opportunity policies
- `sunlightFit.ts` — placement-local sunlight-fit evaluation
- `plant.ts` and `source.ts` — domain types

The processing model is:

```text
garden state + structured knowledge
                ↓
       deterministic evaluation
                ↓
      structured current findings
                ↓
          React explanation
```

This boundary is discussed in more detail in [docs/reasoning-engine.md](./docs/reasoning-engine.md).

## Spatial Rules

The spatial primitive is Euclidean distance between two placement positions, in inches. Rules that need proximity compare the focus placement against every other placement directly. At expected garden sizes, a pairwise scan is cheap and simpler than any spatial index, so no quadtree, R-tree, spatial hash, or cached neighbor graph is used. Add one only if measured performance requires it.

### Relationships

Companion and incompatible relationships are symmetric. They apply to placements whose Euclidean distance from the focus placement is **≤ 12 inches** (`COMPANION_INTERACTION_DISTANCE`, inclusive).

The 12-inch value is a product rule that preserves V1 behavior, not a horticulturally sourced distance. For plants at the centers of 12-inch cells, orthogonal neighbors are exactly 12 inches apart and diagonal neighbors about 16.97 inches apart, so the rule reproduces the original orthogonal-adjacency behavior for grid layouts; it applies to actual distances for free placement. It does not vary per plant or per pair.

If conflicting rules exist for a pair, incompatibility wins defensively; data tests are intended to prevent such conflicts from being authored.

### Spacing

Spacing applies only between placements with the same plant ID. A violation exists when the Euclidean distance between them is less than the plant's sourced minimum spacing in inches; a distance exactly equal to the minimum is valid. Cross-species spacing is not inferred from same-species horticultural guidance.

Spacing values are physical values from cited sources, not conversions of the former abstract tiers. `spacingInches` is currently required: every catalogue plant has sourced spacing, enforced by a data test. If a plant ever cannot be sourced, making the field optional must come with a distinct "not modeled" presentation. Missing spacing must never be shown as "no spacing problem."

### Composition

Composition reports whether a modeled ecological role is represented by at least one placed plant type. It does not assign magnitude, coverage, or quality, and duplicate placements do not increase a role's strength.

### Opportunities

Opportunities are explicit product policies rather than deductions from every missing property:

- a garden-wide suggestion when pollinator support is absent
- local companion candidates for an inspected placement that currently has no modeled companion within the interaction distance

The spatial scope of a conclusion cannot be more precise than its underlying data. A garden-wide observation cannot justify a location-specific recommendation.

### Sunlight Mapping

Sunlight is a user-declared category per environmental cell: full sun, partial sun, or shade. It is not measured irradiance or a simulation. A placement's sunlight is read from the environmental cell containing its position (see [Environment](#environment)).

### Sunlight Fit

Each plant curates the sunlight categories it accepts as an unordered set — a categorical membership test, not a scale, so there is no "too much" or "too little" sun, only accepted or not accepted. `evaluateSunlightFit` (`domain/sunlightFit.ts`) derives the plant from `GardenState` and a placement id rather than accepting it as a separate argument, so the evaluated plant can never disagree with what's actually placed there. It reports one of four statuses — `fit`, `mismatch`, `unmodeled-cell`, or `unmodeled-requirement` — and the two "unmodeled" statuses are never collapsed into `mismatch`: insufficient information is a distinct conclusion from a known incompatibility.

## Explanation Boundary

Domain evaluators return structured objects containing placement ids, plant identities, distances, rule types, roles, or required distances. React components turn those results into concise messages for immediate feedback, persistent inspection, composition summaries, and opportunities.

This keeps user-facing language replaceable without duplicating gardening rules in JSX. The application deliberately avoids an opaque score or a universal finding schema.

## Testing Strategy

Pure domain behavior and data invariants are tested with Vitest. Coverage focuses on:

- valid and invalid garden dimensions and positions, including non-grid positions
- immutable state transitions
- placement, movement, removal, clearing, and environment lifecycle
- position-to-cell mapping, including positions on cell boundaries and near the garden's far edges
- relationship symmetry, the inclusive 12-inch interaction boundary, diagonal exclusion on the 12-inch grid, and conflict handling
- screen↔inch conversion, input rounding, and the half-open boundary (`canvasGeometry`)
- spacing-envelope and drag-highlight derivation (`spacingPreview`)
- scale-bar length selection (`canvasGeometry`)
- art tooling: background keying (`scripts/remove-background`), and texture periodicity, determinism, and the plank seam blend (`scripts/textures`)
- spacing boundaries (exactly at the minimum vs just under it) and deduplication
- composition and opportunity policy behavior
- sunlight-fit status derivation, including both "unmodeled" cases staying distinct from a mismatch
- unique data identifiers and valid provenance references

Native drag-and-drop, plant and bed dragging, zoom and pan, responsive layout, and other primarily visual interactions are verified manually in the browser. A browser-testing dependency has not been added because the current domain behavior can be tested without one.

## Deliberate Limitations

The garden is a simple physical rectangle. Positions are design intent rather than surveyed measurements, and plants are modeled as points: there are no footprints, mature spread, or clearance reasoning yet. Beds are layout only: no rule reasons about them yet. The application also does not currently provide persistence, accounts, climate/location reasoning, soil or water simulation, canopy/shade simulation, arbitrary garden boundaries, 3D rendering, or AI-generated recommendations. Persistence is planned; see [Planned Persistence Direction](#planned-persistence-direction).

If an LLM is introduced later, deterministic data and domain rules should remain the source of horticultural facts and conclusions. An LLM may assist with explanation, comparison, or interaction, but should not invent the underlying gardening rules.

## Planned Persistence Direction

The application remains client-side until accounts are introduced (see PRODUCT.md, [Polish, Landing, and Accounts](PRODUCT.md#polish-landing-and-accounts)). Persistence is staged:

1. **Local save** — the current `GardenPlan` (name, garden, inventory, `schemaVersion`) is saved to `localStorage` and validated on load; an invalid or unknown version is discarded rather than trusted.
2. **Accounts** — Supabase provides magic-link authentication and PostgreSQL. A `gardens` table stores each plan as `jsonb`, owned by a user and protected by Row Level Security, so the client talks to Supabase directly and there is no custom backend server. A user can have several gardens; a local garden is uploaded on first sign-in. Hosting is static (Vercel).
3. **Structured knowledge storage** (possible, later) — plant metadata, relationships, and provenance stay in `src/data` until the dataset is large enough to justify moving them.

The boundary extends rather than changes: persistence stores plans; the domain layer understands and manipulates gardens; the reasoning engine evaluates gardens; the UI presents and edits them. `GardenState` and the deterministic operations stay independent of React, Supabase, or any storage representation, and the reasoning engine never operates on database rows.

The landing page and the planner are separate pages of one Vite multi-page build (`/` and `/plan/`), so no client-side router is needed.
